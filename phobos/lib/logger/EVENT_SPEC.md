# PHOBOS Logger — Event Specification

Version: 1.0

---

# 1. Purpose

The PHOBOS Logger is a system-wide security and activity
monitoring subsystem.

It records relevant activities occurring on the host system,
independent of whether the activity was caused by PHOBOS itself.

The collected events are later used for:

- activity history
- security analysis
- anomaly detection
- security alerts
- severity ranking
- security summaries
- graphical visualization

---

# 2. Event Structure

Every event must contain the following fields.

| Field | Type | Required | Description |
|---|---|---:|---|
| `id` | string | yes | Unique identifier of the event |
| `timestamp` | ISO 8601 | yes | Time at which the event occurred |
| `category` | enum | yes | Type of event |
| `action` | enum | yes | Specific action |
| `user` | string | yes | User involved in the event |
| `source` | string | no | Source of the action |
| `target` | string | no | Target of the action |
| `device` | string | no | Device involved in the event |
| `status` | enum | yes | Result of the action |
| `severity` | enum | yes | Security relevance |
| `details` | string | no | Additional information |

---

# 3. Event ID

Every event receives a unique identifier.

The ID is 16 random bytes rendered as 32 lowercase hexadecimal
characters (generated with `openssl rand -hex 16`).

Example:

id=9f2c1a7b40d84e5f8a6c3b1d0e2f4a57

The ID must uniquely identify one event.

---

# 4. Timestamp

The timestamp uses ISO 8601.

Example:

2026-10-08T20:15:32+02:00

The timestamp represents the time at which the
observed event occurred, not necessarily the time at
which PHOBOS processed it.

# 14. Security Summary

The Logger provides a summarized view of important
events within a selected time range.

Supported time ranges will include:

- last hour
- last 6 hours
- last 24 hours
- last 7 days
- last 30 days
- custom time range

Events are ranked by severity.

Priority:

CRITICAL
HIGH
MEDIUM
LOW
INFO

Events with the same severity are sorted by timestamp.

---

# 15. Alerts

Alerts are generated when an event or combination
of events requires user attention.

An event may appear in the Security Summary without
creating an alert.

Example:

A USB drive being connected may be a MEDIUM event
without generating an alert.

Multiple failed logins combined with unusual file
activity may generate a HIGH or CRITICAL alert.

---

# 16. Anomaly Detection

The Logger will analyze events for unusual behavior.

Examples:

- repeated failed login attempts
- unusual file activity
- unusual external storage activity
- unexpected permission changes
- unusual process activity
- unusual network activity
- combinations of otherwise harmless events

Anomaly detection may generate new SECURITY events.

Example:

category=SECURITY
action=ANOMALY_DETECTED

# 19. Storage & Integrity

Events are appended to a single log file (`events.log`). Each event is
followed by a line with the SHA-256 hash of the previous chain hash
concatenated with the event body, and then a `---` separator.

```
id=...
timestamp=...
...
details=-
event_hash=<sha256>
---
```

Because every hash depends on the previous one, altering, removing or
reordering any earlier event invalidates all later hashes. The final hash
is also stored in `chain.hash`. `phobos logger verify` recomputes the whole
chain and reports the first inconsistency it finds.

Storage locations (overridable via the `LOGGER_DIR` environment variable,
primarily for testing):

- `LOGGER_DIR` — `/var/lib/phobos/logger` (mode `700`)
- `events.log` — the event log (mode `600`)
- `chain.hash` — current chain tip (mode `600`)
- `net/` — per-interface network byte-counter baselines (mode `700`)

# 20. Collectors

Collectors normalise raw system input into schema events. Each collector
returns `0` when it recognizes the input and `1` otherwise.

Three input channels exist:

- **journal** — raw log lines (authentication, sudo, ...)
- **udev** — device events read from udev environment variables
- **audit** — Linux Audit records (state-changing file operations) grouped by
  their `audit(<sec>.<ms>:<serial>)` id

Collectors live in `collector/`, one file per channel; `collector.sh` is the
entry point and sources them all:

- `collector/collector_drive.sh` — `logger_collect_udev` / `logger_collect_drive`
- `collector/collector_auth.sh` — `logger_collect_auth` (logins/logouts, sshd)
- `collector/collector_sudo.sh` — `logger_collect_sudo`
- `collector/collector_journal.sh` — `logger_collect_journal_line` (router; first
  match wins)
- `collector/collector_user.sh` — `logger_collect_user` maps `useradd`/`userdel`/
  `usermod`/`passwd`/`chsh`/`chfn` and `groupadd`/`groupdel`/`gpasswd` messages to
  `USER` events (`USER_CREATED`/`USER_DELETED`/`USER_MODIFIED`/`GROUP_ADDED`/
  `GROUP_REMOVED`). The actor is not present in the short journal format, so the
  affected account is recorded in `target` (`user:<name>`/`group:<name>`) and
  `user` is `SYSTEM`.
- `collector/collector_system.sh` — `logger_collect_system` maps `systemd`
  messages to `SYSTEM` events: `Startup finished` → `BOOT`, `Shutting down` →
  `SHUTDOWN`, `Rebooting` → `REBOOT`, `Started`/`Stopped <unit>` →
  `SERVICE_STARTED`/`SERVICE_STOPPED`, `Reloading`/`Reloaded` → `CONFIG_CHANGED`.
  All units are recorded.
- `collector/collector_network.sh` — `logger_collect_network` maps
  NetworkManager / `wpa_supplicant` / `systemd-networkd` messages to `NETWORK`
  `CONNECTION`/`DISCONNECTION` events. The WiFi SSID is captured in `target`. A
  per-interface state file under `$LOGGER_DIR/net` records the byte counters at
  connect time; on disconnect the `rx_bytes`/`tx_bytes` deltas are added to
  `details`. The state file also deduplicates the overlapping sources. Volume is
  approximate and unavailable if the collector restarts mid-connection.
- `collector/collector_process.sh` — `logger_collect_process` maps kernel crash
  messages (`segfault`, `traps:` general protection fault, OOM killer, kernel
  BUG, paging request, panic) to `PROCESS` `CRASH` events. Process `START`/`STOP`
  are intentionally not tracked (very high volume; see §18).
- `collector/collector_audit.sh` — `logger_collect_audit_block` maps a coalesced
  audit block to a single `FILE` event (`CREATE`/`DELETE`/`MOVE`/`RENAME`/
  `MODIFY`). Source/target are taken from `PATH` records by `nametype`
  (`PARENT` records name a directory, never the file). A writable open whose
  `PATH` record is `nametype=CREATE` is a creation (`CREATE`); a writable open
  whose `PATH` record is `nametype=NORMAL` means the file already existed and
  was modified in place (`MODIFY`). Actors are limited to real users
  (`auid>=1000`) and the sudo helper's own file operations are ignored.
- `collector/collector_audit.sh` also maps blocks with the `phobos-permission`
  key to a `PERMISSION` event: `chmod`/`fchmod`/`fchmodat` →
  `PERMISSION_CHANGED`, `chown`/`fchown`/`lchown`/`fchownat` → `OWNER_CHANGED`,
  `setxattr`/`lsetxattr`/`fsetxattr` → `ACL_CHANGED`. The affected path is taken
  from the `PATH` record, the actor from the audit `auid`.

Each channel has an entry point that feeds the collectors:

- journal: `logger_journal.sh` reads lines from stdin. The
  `phobos-logger-journal.service` unit installed by `phobos logger enable`
  runs `journalctl -f -o short -n 0 | logger_journal.sh`. A single line can
  be fed manually with `phobos logger ingest "<line>"`.
- udev: `logger_udev.sh` is run by the udev rule installed by
  `phobos logger enable`.
- audit: `logger_audit.sh` reads records from stdin, coalesces them by audit
  id, and flushes each block. The `phobos-logger-audit.service` unit (installed
  by `phobos logger enable`) runs
  `tail -F -n 0 /var/log/audit/audit.log | logger_audit.sh`. Rules are installed
  to `/etc/audit/rules.d/50-phobos-file.rules` (key `phobos-file`) and
  `/etc/audit/rules.d/51-phobos-permission.rules` (key `phobos-permission`) and
  loaded with `augenrules --load`. A single block can be fed manually with
  `phobos logger ingest-audit "<block>"`.

Adding a new source means adding a file under `collector/` and sourcing it from
`collector.sh` (and, for journal sources, adding it to the router in
`collector_journal.sh`).
